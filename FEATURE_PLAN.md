# Dialog Auth — план следующих изменений

Исторический снимок плана на 2026-11-16. Описанные ниже состояние, пути, версии и задачи относятся к этой дате и не отражают последующие изменения production или реализации.

Этот файл предназначен для продолжения работы через Kimi Code. Сначала прочитать его целиком, затем изучить текущий код и тесты. Не начинать с переписывания архитектуры вслепую.

## 1. Текущее состояние

Рабочая база находится на VPS в `/root/dialog-auth-fabric-1.5.2/source/`.

Собранные артефакты: `/root/dialog-auth-fabric-1.5.2/artifacts/`.

В рабочей базе версия 1.5.2:

- companion не зависит от установки серверного `dialogauth` на клиенте;
- общие protocol/crypto/accessor-классы упакованы в companion;
- серверный `AuthTask` не входит в companion;
- клиентский ZIP и modpack не содержат серверный JAR;
- добавлен `CompanionGate`, работающий на `BEFORE_CONFIGURE`, после согласования каналов, но до Fabric registry sync;
- клиенту без обязательного companion отправляется отдельное сообщение с `client-download-url`, а не ошибка про неизвестные записи `trmt`;
- если companion-канал присутствует, gate пропускает configuration дальше;
- чистая сборка прошла, 54 теста, 0 ошибок;
- ранний disconnect проверен протокольным клиентом на временном сервере с `trmt`;
- полноценный графический Minecraft-клиент с новым UI не тестировался.

Production `/opt/minecraft-fabric/` на момент составления плана всё ещё использует `dialog-auth-1.5.0.jar`. Версия 1.5.2 туда не установлена. Не обновлять и не перезапускать production без отдельного явного запроса пользователя.

GitHub main и PR не считать обновлёнными: публикация ранее была заблокирована отсутствием `contents:write`.

## 2. Главная цель

Получить две независимые части:

1. Серверный мод Dialog Auth: аккаунты, регистрация/вход, сессии, rate limits, handshake, проверки совместимости.
2. Один универсальный клиентский companion: шифрование, серверные профили доверия, UI, добровольная установка/обновление модпака.

Не создавать уникальный клиентский JAR под каждый сервер. Не зашивать приватные ключи, адреса доверия или серверные секреты в companion.

Сервер может упаковывать готовые JAR в клиентскую сборку, но не компилировать моды во время работы.

## 3. Чего явно не делать

- Не форкать и не патчить Fabric Loader отдельным дистрибутивом.
- Не добавлять WebView в Minecraft. Ссылки открываются в системном браузере или показываются текстом.
- Не копировать автоматически все файлы из серверного `mods/` в клиентскую сборку.
- Не полагаться на `environment=*` как доказательство того, что мод обязателен клиенту. На текущем сервере даже backup/antixray/server mods имеют `environment=*`.
- Не загружать новые JAR на лету. После изменения модов требуется полный перезапуск клиента.
- Не добавлять hardware ban по CPU/DMI/machine-id. Он ненадёжен, подменяется клиентом и создаёт лишние privacy-риски.
- Не считать список модов или installation UUID античитом: модифицированный клиент может отправить любые данные.
- Не добавлять собственные типы диалогов в реестры Minecraft, если то же самое можно сделать custom payload + client `Screen`: новые registry entries снова создадут проблемы синхронизации.

## 4. Конфигурация

Расширить существующий `config/dialogauth/config.properties`, сохранив обратную совместимость значений по умолчанию.

Предлагаемые параметры:

```properties
# Создавать ли ZIP/manifest из готовых клиентских JAR.
client-distribution-enabled=true

# vanilla — текущий NoticeDialog; companion — собственный клиентский Screen.
auth-ui=vanilla

# Внешний готовый universal companion, который раздаётся без изменений.
client-companion-jar=

# Явные списки id модов, а не автоматическое копирование всего mods/.
# Ниже — server-specific пример, а не generic defaults: trmt и cloth-config
# обязательны только при явном выборе этих модов для конкретного сервера.
client-required-mods=fabric-api,trmt,cloth-config,dialogauth-companion
client-optional-mods=voicechat

# Существующие параметры сохранить.
client-download-url=
client-modpack-manifest-url=
client-modpack-servers=
require-encrypted-auth=true
```

Правила:

- `client-distribution-enabled=false` полностью отключает создание ZIP/manifest, но не отключает `client-download-url`.
- `auth-ui=vanilla` сохраняет текущий NoticeDialog. Companion всё равно может быть обязателен для encrypted offline auth.
- `auth-ui=companion` автоматически делает companion обязательным и включает ранний gate даже там, где encrypted offline auth не используется.
- Не смешивать UI-режим и требование шифрования: это разные настройки.
- Некорректные сочетания, отсутствующие обязательные JAR, неизвестные mod id и небезопасные имена файлов должны давать понятную ошибку при старте.
- Не включать в клиентский конфиг приватные ключи, reset token, accounts или серверные настройки.

Добавить тесты на defaults, оба UI-режима, отключённую раздачу и ошибочные конфигурации.

## 5. Раздача клиентской сборки

Оставить два независимых способа:

### Готовая сборка

- Сервер берёт только явно перечисленные готовые JAR.
- Universal companion берётся как готовый файл, а не собирается из исходников на VPS.
- Сформировать начальный ZIP и последующий `manifest.json`.
- Для каждого файла записывать id, версию, имя, размер, SHA-256, required/optional и доступные homepage/sources.
- Подписывать manifest отдельным modpack signing key.
- Использовать staging, временные файлы и атомарную замену. Не оставлять наполовину обновлённую раздачу.
- Серверный `dialogauth` не включать в клиентскую сборку.

После перехода на внешний `client-companion-jar` можно убрать embedded companion resource и runtime `ClientKitGenerator` в старом виде. Сборочная Gradle-связь server/companion может остаться для общей сборки релиза, но серверный runtime не должен требовать companion resource внутри собственного JAR.

### Ручная установка

Пользователь должен иметь равноправную альтернативу без автоматической записи в `mods/`:

- точный список required/optional модов и версий;
- ссылки homepage/sources, извлечённые из `fabric.mod.json`, если они есть;
- SHA-256 для самопроверки;
- кнопка/команда «проверить снова» после ручной установки;
- сервер принимает установленные файлы по правилам совместимости независимо от того, откуда пользователь их скачал.

Ссылки `sources` не считать ссылками на готовый JAR. Для автоматического внешнего скачивания нужны закреплённые URL/версии и SHA-256, а не изменяющийся `latest`.

Проверить условия лицензий перед перераспространением чужих JAR.

## 6. Окно подтверждения установки

До записи файлов в `mods/` показать:

- адрес и стабильный server id;
- список устанавливаемых/обновляемых/удаляемых модов;
- old version -> new version;
- required/optional;
- размер и SHA-256;
- fingerprint modpack signing key;
- предупреждение, что после перезапуска JAR выполняется как обычный Java-код.

Кнопки: «Проверить и установить», «Установить вручную», «Отмена», «Скопировать отчёт».

Порядок:

1. Скачать manifest и публичный ключ.
2. Проверить подпись manifest.
3. Показать предупреждение и состав изменений.
4. Только после согласия скачать JAR в staging.
5. Проверить SHA-256 каждого файла.
6. Атомарно установить файлы и убрать старые managed versions в backup.
7. Потребовать перезапуск.

SHA-256 доказывает совпадение с manifest, но не подлинность самого manifest. Подлинность обеспечивается доверенной подписью.

Политика подтверждения:

- первое доверие серверу — явное подтверждение;
- смена ключа — блокировка и обязательное новое подтверждение со старым/новым fingerprint;
- неверная подпись или SHA-256 — отказ без кнопки «всё равно установить»;
- обычные обновления тем же ключом могут быть automatic/ask согласно отдельной настройке;
- выбор и доверие хранить отдельно для каждого сервера.

При первом подключении companion ещё отсутствует, поэтому оба варианта установки должны быть доступны на веб-странице. In-game window появляется только после установки companion.

## 7. Trust store и серверные профили

Сейчас `auth-server-public.key` и `modpack-public.key` глобальные, что мешает корректно работать с несколькими серверами.

Нужно:

- ввести стабильный `server-id`, не зависящий от смены DNS-имени;
- хранить отдельный профиль на сервер, например `config/dialogauth/servers/<safe-server-id>/`;
- разделить адреса сервера, auth identity, modpack manifest URL и modpack signing key;
- не использовать один глобальный pinned key для всех серверов;
- при смене адреса сохранять identity, а при смене ключа требовать подтверждение;
- auth identity key и modpack signing key оставить разными.

Сертификаты можно добавить позже как подписанную CA привязку `server-id`/адресов к публичным ключам. Самоподписанный сертификат, скачанный без независимой проверки, не даёт большей безопасности, чем TOFU. Приватные ключи никогда не покидают сервер.

## 8. UI регистрации и входа

Сохранить два режима.

### `auth-ui=vanilla`

- Использовать текущий `AuthTask` и `NoticeDialog`.
- Companion при наличии продолжает шифровать ответ.
- Не менять поведение по умолчанию.

### `auth-ui=companion`

- Сервер отправляет версионированный custom payload: register/login, ошибка, параметры политики пароля.
- Companion открывает собственный `Screen`.
- Поддержать регистрацию, вход, повтор пароля, ошибку, занято/таймаут, отмену/выход.
- Не передавать пароль через открытый dialog click в этом режиме.
- Использовать существующий encrypted handshake и response sequence protection.
- Не добавлять новые dialog registry types.
- Все строки вынести отдельно и сохранить русский UI.

## 9. Сетевой порядок

Целевой порядок на configuration-фазе:

1. Fabric channel negotiation.
2. `BEFORE_CONFIGURE`: проверка обязательного companion.
3. Если companion отсутствует — собственный disconnect с коротким `client-download-url`; registry sync не должен маскировать сообщение.
4. Если реализована проверка модов — запрос/проверка mod list до registry sync. Это compatibility gate, не античит.
5. Fabric/vanilla configuration и registry sync.
6. Авторизация до входа в мир, с соблюдением текущего task lifecycle.

Не переносить начальную загрузку модпака в игровой handshake: при несовпадающих реестрах соединение может быть разорвано раньше. Начальная раздача идёт по HTTPS до подключения.

Не вызывать напрямую vanilla `onTaskFinished` для ранних Fabric tasks. Для ранней задачи использовать `FabricServerConfigurationNetworkHandler.completeTask`, либо оставить текущую синхронную проверку без task, если отдельная задача не нужна.

## 10. Веб-страница

Использовать существующий сайт проекта, без WebView и без обязательного JavaScript.

На странице загрузки:

- готовая сборка;
- ручной список модов и точных версий;
- ссылки на проекты/источники;
- SHA-256 и fingerprint;
- инструкции Prism и Pojav;
- обязательный перезапуск после установки.

`client-download-url` должен вести на понятную страницу, а не обязательно напрямую на JAR.

## 11. Карта текущего кода

- `DialogAuth.java` — инициализация, конфигурация, gate и network handlers.
- `CompanionGate.java` — текущая ранняя проверка companion.
- `AuthTask.java` — vanilla UI и серверная auth task.
- `DialogAuthPayloads.java` — protocol payloads.
- `SecureServerSession.java`, `SecureClientHandler.java`, `AuthCrypto.java` — handshake и шифрование.
- `DialogAuthClient.java` — инициализация companion.
- `AuthServerTrustStore.java` — текущий глобальный auth key pin, требует переработки.
- `ModpackTrustStore.java` — текущий глобальный modpack key pin, требует переработки.
- `ModpackSync.java`, `ModpackInstaller.java`, `ModpackManifest.java` — загрузка и установка сборки.
- `ClientKitGenerator.java` — текущая упаковка начального ZIP.
- `website/` — download/reset backend и страницы.

## 12. Порядок выполнения для Kimi Code

Работать небольшими проверяемыми этапами, не одним гигантским коммитом:

1. Добавить конфигурацию и тесты совместимости defaults.
2. Перевести раздачу на explicit allowlist и внешний universal companion.
3. Реализовать manual install report/страницу и готовую сборку.
4. Добавить confirmation UI, staging и signature/hash checks.
5. Сделать per-server trust store и миграцию старых глобальных ключей без молчаливого доверия новому ключу.
6. Добавить companion UI и protocol versioning, сохранив vanilla mode.
7. Обновить README, примеры конфигурации и CI artifacts.
8. Только после тестов предложить отдельный deploy план, но не выполнять его без явного запроса.

## 13. Критерии приёмки

- `JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64 bash ./gradlew --no-daemon clean build generateModpack` проходит.
- Все старые и новые тесты зелёные.
- `verifyCompanionStandalone` продолжает работать или заменяется эквивалентной проверкой.
- Companion устанавливается без серверного `dialogauth` на клиенте.
- В клиентской раздаче нет серверного JAR, секретов, accounts, world или приватных ключей.
- Серверные моды не попадают в сборку без явного разрешения в allowlist.
- При отсутствии companion и наличии `trmt` клиент получает download instructions, а не `Received ... registry entries`.
- При companion-канале gate не блокирует configuration.
- Пользователь может выбрать готовую сборку или ручную установку.
- До подтверждения ничего не записывается в `mods/`.
- Подпись/SHA-256 проверяются до установки.
- Смена ключа не проходит молча.
- Два разных сервера не конфликтуют из-за глобального pinned key.
- При изменении модов требуется перезапуск, а не попытка runtime loading.
- Production не меняется без отдельного явного запроса.

## 14. Git и публикация

- Работать в отдельной ветке.
- Не пушить напрямую в main и не merge PR без явного запроса.
- Перед PR показывать краткий diff и результаты тестов.
- Не коммитить токены, SSH keys, reset tokens, signing keys, identity keys или account stores.
